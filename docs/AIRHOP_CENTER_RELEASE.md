# Единый релиз AirHop Center

Этот документ — текущий порядок подготовки **локального/demo-кандидата**, а не
подтверждение публикации. Apple notarization, HQ и отдельная сборка Hugo сюда
не входят. Сервер не обновляется автоматически. Код и инструкции хранятся в
общем репозитории: настройки, аккаунты и секреты конкретного центра не должны
попадать в исходники или распространяемый архив.

## Одна версия

- Версия приложения берётся из четырёх согласованных desktop manifests/lockfile.
  Версии отдельных Rust-библиотек независимы: их не переименовываем ради номера
  продукта. Общая принадлежность артефактов определяется SHA исходников.
- Идентификатор: `airhop-center-<version>-<12 символов commit SHA>`.
  Полные SHA коммита и дерева записываются в `release.json`.
- Настройки Mac-приложения показывают версию и короткий SHA. Полный идентификатор
  доступен в подсказке. Публичная форма получает тот же `airhop-release.json`;
  серверный Dockerfile — те же version/revision/release labels.
- Источник — **один чистый локальный коммит**. Подготовка отказывает при любых
  staged, unstaged или untracked изменениях; повторная проверка проводится в
  процессе сборки и перед завершением. Ни одна утилита не делает commit/push.
- Артефакты складываются в новую уникальную временную папку. Старые папки не
  перезаписываются. Установленное приложение не заменяется при сборке.

## Подготовка

Активировать Hermit и убедиться, что нужные изменения закоммичены. Затем:

```sh
. ./bin/activate-hermit
node scripts/prepare-airhop-center-release.mjs '<проверенный-demo-image>:<точный-tag>' 'sha256:<полный-локальный-image-ID>'
```

Команда выводит `output` — новую папку кандидата. Она содержит:

- `source.tgz` из exact Git commit, без `.env*`, файлов ключей/БД и build outputs;
- `source-manifest.json` с полным перечнем файлов и SHA-256; архив сравнивается
  побайтно с файлами, используемыми локальной сборкой;
- `release.json` с идентичностью исходников и максимальной миграцией;
- `base-image.json` с отдельными local image tag и config ID. Локальный Docker
  image ID нельзя подставлять после `@sha256:` как registry manifest digest.
  Перед сборкой и после неё надо сверить `.Id` указанного tag с этим файлом;
  `latest` и неявные теги не принимаются;
- `Dockerfile.center-release`, который сохраняет pinned demo runtime/pilot и
  старые hashed assets, но пересобирает серверные бинарники. Для shared VPS
  ограничены и `cargo chef cook`, и сборка Rust (`CARGO_BUILD_JOBS=1`).

Это не передача данных: SSH/SCP и публикации в этих утилитах нет. Перед внешней
передачей нужен просмотр состава архива и разрешение на конкретное назначение.

## Сборка и проверка

На Mac с установленными зависимостями:

```sh
node scripts/build-airhop-center-candidate.mjs '<output>'
node scripts/verify-airhop-center-candidate.mjs '<output>' --require-current
```

Сборщик использует lockfiles, default system-keyring и один `AIRHOP_RELEASE_COMMIT`
для native и public-web. Сохраняет production public-web, отдельную копию app
bundle, build logs и `artifacts.json` с контрольными суммами. Локальная ad-hoc
подпись проверяется `codesign --verify --deep --strict`; это **не** notarization.
Повторная сборка в ту же папку запрещена, включая незавершённую попытку.

Нативный frontend собирается в `<output>/native-web`, фиксируется по SHA-256 и
передаётся Tauri через отдельный `tauri.candidate.json`. Общий `desktop/dist`
не используется как источник app bundle: его могут перезаписывать dev/CI-сборки.
Receipt версии 2 также проверяет native-web и конфигурацию упаковки. Если в общей
рабочей папке продолжаются новые изменения, сборку выполняют из отдельного clean
checkout зафиксированного коммита; незавершённые правки в релиз не подмешивают.

`verify` сверяет оба встроенных release receipts, архивы, Dockerfile, полный
набор файлов и их SHA-256. `--require-current` дополнительно запрещает выдавать
старый, хотя и целый кандидат за текущую версию проекта. Непомеченные обычные
dev/CI-сборки не являются кандидатом; для них нужен этот же цикл подготовки.

Проверки согласованности версии и release identity входят в `pnpm check` и,
следовательно, в `just ci`. `just airhop-center-open` также требует clean commit
и встраивает его identity; это **отдельная устанавливающая команда**, не этап
подготовки кандидата. Для согласованного demo rollout её не запускать до
прохождения серверного preflight.

## Выкладка в выбранное окружение

Целевой домен подтверждается перед выкладкой. Тестовый «Хюге» сейчас находится
на `demo.airhop.ru`; соседний `buzz-prod` — другое окружение. Нельзя выбирать
его по слову «прод» или менять вместе с demo. Для нового центра используются
его собственные домен, Compose project, база, volumes и секреты.

Требуемая схема указана в `release.json.databaseMigration`, текущая — в
`_sqlx_migrations`. Сначала заново проверить состояние выбранного окружения,
создать backup, восстановить его в отдельную preflight-БД и применить там
все недостающие миграции. Для объединённого пакета агентов 0.5.13 это 0065 и
0066 поверх схемы 64: политики/обязанности и защита от повторных ответов.
Затем
собрать образ из `source.tgz`, `public-web.tgz`, `release.json` и сгенерированного
Dockerfile, target `airhop-center-candidate`. Использовать immutable release ID,
не `latest`. Прежние assets/pilot остаются из точно указанного base image.

В общем кандидате изменены также shared-thread gateway и контракт Hermes.
По отдельному разрешению обновлять согласованно только demo relay, Telegram
gateway и Hermes runtime/ACP/CLI/MCP/persona из того же commit, с полной
существующей Compose overlay chain. Локальная сборка не создаёт серверные Docker
образы и не выполняет этот rollout; их нужно собрать из того же source.tgz.
Старый Hermes или gateway оставлять рядом с новым relay нельзя.
Подтвердить image labels всех трёх сервисов, схему БД, доступность сайта и формы,
авторизацию, реальные отчёты и изоляцию двух клиентских тредов; отдельно проверить
неизменность production и соседних контейнеров. Лишь затем
сохранить резервную копию установленного app bundle и установить **app из папки
проверенного кандидата**, а не из изменяемого `desktop/src-tauri/target`.
Аккаунт, Keychain и данные не удалять. Системные запросы macOS подтверждает сам
пользователь. Для старого SQLx binary rollback требует `BUZZ_AUTO_MIGRATE=false`.

## Внутренние агенты при новом развёртывании

После обновления relay и схемы установить закреплённый runtime на компьютере,
который запускает внутренних агентов:

```sh
scripts/install-airhop-hermes-team.sh
```

Установщик сохраняет обычный Hermes и существующие установки; настройка
провайдера выполняется отдельно, ключи не встраиваются в приложение. Порядок
настройки и проверки: [Hermes для команды](../integrations/hermes-airhop-team-runtime/README.md).
Владелец центра проверяет/согласует состав команды после обновления.
Внутренние агенты пока работают через desktop runtime, а не как серверные
процессы 24/7. Родительский Hermes и Telegram gateway остаются серверными.

## Обновления приложения

Center проверяет канал при запуске и затем раз в шесть часов. Пакет скачивается
и проверяется автоматически, но установка/перезапуск выполняются только по
нажатию пользователя. Есть ручная проверка в настройках и повтор после ошибки.
Отсутствие сети или подписи не выдаётся за «установлена последняя версия».

Открытый ключ и адрес канала находятся в `deploy/airhop/desktop-updater.json`.
Сборщик кандидата встраивает их в native config; для отдельного fork задать
оба `AIRHOP_UPDATER_PUBLIC_KEY` и `AIRHOP_UPDATER_ENDPOINT` своей организации.
Закрытый ключ **никогда** не входит в исходники, артефакты или журналы сборки.
На GitHub используются секреты `TAURI_SIGNING_PRIVATE_KEY` и
`AIRHOP_UPDATER_PUBLIC_KEY`; пароль ключа, если задан, —
`TAURI_SIGNING_PRIVATE_KEY_PASSWORD`. Потеря закрытого ключа требует ручного
перехода пользователей на новую доверенную сборку: ключ нужно резервировать.

`.github/workflows/airhop-macos-release.yml` требует согласованную версию в
коммите, собирает подписанную/notarized macOS-сборку в draft release, проверяет
подпись реального загруженного updater-архива и только затем публикует релиз.
`airhop-center-latest/latest.json` обновляется последним и ссылается на архив
в версионном релизе. Повтор версии и понижение номера запрещены. Сейчас
автоматический канал рассчитан на Apple Silicon; несуществующие сборки других
платформ в манифест не добавляются. Сертификат Apple и notarization — отдельные
от ключа Tauri реквизиты, без них этот публичный workflow останавливается.

Для тестовой ad-hoc сборки можно подписать архив уже проверенного кандидата
штатной `tauri signer sign`; это не делает приложение Apple-notarized.
Перед публикацией проверить его через `desktop/scripts/verify-airhop-updater.mjs`,
сформировать feed через `desktop/scripts/write-airhop-updater-manifest.mjs` и
сохранить явную пометку тестовой сборки. Не публиковать такой пакет как
подписанный Apple production-релиз.

Приёмка: новая версия вызывает предложение; без нажатия установка не идёт;
повторное нажатие не запускает вторую установку; испорченная подпись, сеть и
ошибка установки не перезапускают приложение; актуальная версия не предлагает
обновиться; после установки сохраняются аккаунт, настройки и release identity.
Старые сборки с отключённым updater требуют **одного ручного обновления**.
