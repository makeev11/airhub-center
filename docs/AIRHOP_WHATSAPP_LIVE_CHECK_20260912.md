## Проверка публичного webhook

Фактический callback из Meta App subscriptions:

`https://airhop-center.srv1610606.hstgr.cloud/webhooks/whatsapp/ff334f06-56ee-4638-8801-69f94ff10618`

На него отправлены три **пустых** пакета (`messages=[]`, `statuses=[]`):

| Проверка | Фактический ответ |
|---|---|
| Правильная HMAC-подпись и номер подключения | `200 ok` |
| Неправильная подпись | `401 invalid signature` |
| Правильная подпись, другой phone_number_id | `403 connection mismatch` |

Подписи сформированы внутри существующего gateway; app secret не передавался
на локальную машину. Пакеты не содержат сообщений или клиентских данных.
Это доказывает доступность публичного обработчика и проверку подписи/номера,
но не заменяет тест доставки сообщения из Meta на реальный телефон.

Из самого demo-сервера и его gateway обращение к этому внешнему callback
завершается ConnectTimeout; с внешней машины все три проверки успешны.
Причина ограничения сетевого маршрута не установлена. Общий отказ webhook
этим таймаутом не подтверждается.

Callback пока использует временный Hostinger ingress в Литве. Домен
`hooks.airhop.com.br` не разрешается в DNS. Перенос в Бразилию, описанный в
плане подключения, ещё не выполнен. Relay webhook base URL указывает на
`https://demo.airhop.ru/webhooks/whatsapp`; фактический Meta callback отличается
из-за существующего промежуточного прокси.

## Что блокирует завершение

### Настройки Meta

GET phone number `health_status` возвращает общий `can_send_message=BLOCKED`.
Вложенное состояние WABA указывает ошибку **141006**: проблема со способом
оплаты блокирует **business-initiated conversations**. Meta предлагает добавить
новый способ оплаты. Это не доказательство отказа входящих сообщений или всех
ответов внутри открытого сервисного окна.

Дополнительные ограничения: business verification ещё не пройдена
(`not_verified`, ошибка 141010, состояние BUSINESS LIMITED); display name ещё
не одобрен для повышения лимита (PHONE_NUMBER LIMITED). APP имеет состояние
AVAILABLE. Проверка самого телефонного номера при этом уже пройдена.

В каталоге Meta ровно один шаблон: `hello_world`, `en_US`, APPROVED/UTILITY,
без BODY-параметров. Сервисных шаблонов центра на рабочих языках нет.
Поддержка каталога в коде сама по себе их не создаёт и не одобряет.

### Развёрнутый код и миграции

Текущий relay: `airhub-center-relay:whatsapp-credential-rotation-df472bd`,
source revision `df472bd18e7956bbd9d24ac5cac411d8aa575bc7`.
Gateway: `airhop-hermes-channel-gateway:credential-rotation-df472bd`.

Новая локальная доработка шаблонов и статусов доставки не развёрнута:
gateway сообщает `templates=false`; в live outbox отсутствуют новые поля
`provider_status`, `provider_recipient`, `accepted_at`, `read_at`.

На сервере успешно применены миграции до **69**:

| Номер | Назначение |
|---|---|
| 65 | airhop agent platform |
| 66 | airhop agent reply receipts |
| 67 | airhop conversation reply receipts |
| 68 | airhop whatsapp cloud credentials |
| 69 | airhop effective channel access |

Локальная база разработки — HEAD `a7f5e74`; в рабочем дереве credentials
имеют номер 65, а новая delivery-миграция — 66. Локальная credentials-миграция
побайтово совпадает с live 68, что дополнительно проверено по SHA-512.

**Нельзя накатывать текущее локальное дерево прямо на эту установку.** Оно
конфликтует с уже применёнными миграциями и не содержит часть развёрнутых
изменений. Требуется интеграция на актуальную серверную ревизию с сохранением
65–69 и новым свободным номером для delivery (70, если к моменту подготовки
релиза он всё ещё свободен). Применённые миграции не переименовывать и не менять.

## Порядок завершения

1. Перенести локальную WhatsApp-доработку на актуальную серверную версию;
   проверить совместимость и миграцию с копией схемы/состояния до версии 69.
2. Исправить платёжный метод в Meta Business Account. Данные карты вводятся
   владельцем в интерфейсе Meta; доступы и ключи интеграции уже работают.
3. Подготовить и согласовать сервисные шаблоны центра на нужных языках,
   получить их одобрение в Meta. Завершить оставшиеся проверки бизнеса/имени
   для снятия соответствующих ограничений.
4. Подготовить проверяемое обновление relay, gateway и desktop с резервной
   копией базы и gateway state; затем выполнить контролируемый деплой.
5. Пройти реальный цикл: запись → привязка семьи → входящее → ответ →
   delivery/read, затем одобренный шаблон вне 24 ч и восстановление после сбоя.
6. Завершить запланированный перенос webhook на постоянный ingress с проверкой
   нового callback до отключения действующего прокси.
