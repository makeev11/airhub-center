# Аудит графов агентов Airhop — 11 сентября 2026

Проверена локальная ревизия `277dffa5`, включающая выложенный код Hermes
`00489edf8334`. Это аудит исходников и локальных тестов. В этом аудите не
проверялись текущие серверные логи, установленные версии настольных клиентов,
реальные диалоги и конверсия. Рабочий код и развёртывание не изменялись.

## Вывод

Новый граф управления инструментами подключён только к роли
`parent_administrator` — Hermes, отвечающему родителям. Это полезный, но частичный
автомат состояний одного хода. Единого графового механизма для всех агентов нет.
У команды Welcome существует отдельная, сохраняемая на сервере маршрутизация
между агентами и последовательность знакомства. Это уже управление состоянием,
но оно не задаёт порядок чтений и действий внутри работы каждого специалиста.

Граф знаний «клиент → ребёнок → запись → занятие → подходящая информация» как
отдельный механизм поиска не реализован в проверенном пути агентов. Связи
сущностей существуют в реляционной базе. База знаний ищется SQL-запросом по
опубликованным документам, области доступа, языку и полнотекстовому совпадению.
Наличие `petgraph` в Cargo.lock связано с `prost-build`, а не с графом агентов.

## Что реализовано хорошо

- Вызовы родительского backend проходят через `Dialogue::prepare/observe`;
  это исполняемые проверки, а не только текст в промпте.
- Для одиночного первого приветствия и точного подтверждения готового черновика
  есть жёсткие ограничения лишних операций.
- Непривязанный контакт не может загрузить семейную карточку через этот граф.
  Права и область данных дополнительно проверяет сервер.
- После успешной отправки повторный вызов возвращает квитанцию; серверная
  транзакция также проверяет ход, аренду, владельца диалога и повторную отправку.
- Результат успешного изменения можно повторно использовать после ошибки
  доставки; повторно создавать запись для этого не требуется.
- Booking Core остаётся источником истины: граф не отменяет проверок согласия,
  актуальности версии, доступности и прав.
- Каждый родительский ход начинает новую сессию с ограниченным серверным
  контекстом; черновик записи сохраняется в базе. Локальные счётчики и кэш графа
  сбрасываются при смене разрешения или процесса, а не служат постоянной памятью.

## Подтверждённые недочёты

### 1. P2: отправка обходит обязательную загрузку контекста

`call_parent_backend` требует сначала получить контекст, но `send_parent_reply`
идёт отдельным путём: проверяет форму сообщений и аренду, не требуя загруженного
контекста. Локальный тест воспроизвёл успешную отправку первым вызовом инструмента,
без единого `get_turn_context`. В таком пути не инициализируется и согласованная
пауза последующих ответов. Это пробел в контроле поведения, а не обход серверных
прав доступа. Тест использовал подставной HTTP backend, не реального родителя.

Места: `airhop.rs:1420`, `airhop.rs:1435`, `parent_dialogue.rs:185`.
Исправление: единый допуск отправки, требующий контекст; отдельно определить
ограниченный аварийный ответ, если загрузить контекст невозможно.

### 2. P2: лимит чтений может перекрыть передачу человеку после смены филиала

Воспроизведённая последовательность: контекст + пять разных поисков → назначение
филиала → сброс старого контекста → новое чтение контекста отклоняется, поскольку
шесть чтений уже потрачены. Для `handoff_reason` отправитель должен загрузить
актуальные `handoffTargets`, если кэша нет, и попадает в тот же запрет.
Обычный текстовый ответ остаётся возможным; автоматическая передача сотруднику
внутри этого хода блокируется. Фактическую частоту случая в живых диалогах аудит
не устанавливает.

Места: `parent_dialogue.rs:112`, `parent_dialogue.rs:156`, `airhop.rs:1458`.
Исправление: гарантировать отдельный ограниченный путь получения актуальных
адресатов передачи либо возвращать их вместе с результатом смены филиала.
Не возвращать устаревшие адресаты и не снимать все лимиты в Recovery.

### 3. Лимит backend-чтений не является лимитом циклов модели

Успешный повторный запрос возвращается из кэша до изменения счётчика.
Диагностический тест сделал двадцать повторных чтений контекста: backend был
вызван только один раз, а `remainingReads` оставался равным пяти. Экономия базы
есть, но модель всё ещё может расходовать шаги и токены на такие вызовы.
Отдельные ограничения рантайма и времени хода не равнозначны обнаружению
повторяющихся действий в графе.

Место: `parent_dialogue.rs:84`. Улучшение: отдельно считать попытки инструментов
и повторные запросы без новых данных, сохранив допустимый повтор доставки и
квитанций. Ограничения должны различать сетевую ошибку и отсутствие продвижения.

## Архитектурные ограничения

`ChooseRoute` не классифицирует информационный запрос. Узлы Knowledge, Family
и Options выставляются после выбора инструмента моделью. Для большинства
состояний нет явной таблицы разрешённых переходов; работают общие лимиты и
подсказка `next`. Это сохраняет гибкость при смене темы, но не гарантирует
кратчайший путь «понял вопрос → прочитал нужное → ответил».

У остальных ролей `airhop_read` не использует родительский граф или его кэш.
Каждое такое чтение сначала запрашивает настройки организации, а затем, при
необходимости, отдельный ресурс (`airhop.rs:1560`, `airhop.rs:1972`). Следовательно,
нельзя переносить обещания экономии запросов Hermes на всю команду.

## Рекомендуемый порядок работы

1. Закрыть два подтверждённых пробела Hermes и добавить постоянные регрессионные
   тесты; отдельно ввести ограничение повторов без продвижения.
2. Выделить общие механизмы: идентичность хода, контекст, счётчики, квитанции,
   завершение, обработка ошибок, гарантированная передача человеку и журнал
   переходов. Задать явные допустимые действия для каждого состояния.
3. Подключать роли с собственными сценариями. Fizz нужен маршрут выбора и
   делегирования; аналитику — выбор данных и проверка вывода; администратору —
   просмотр и подтверждение действий; маркетологу — предложение, проверка и
   подтверждение публикации. Родительский сценарий записи им целиком не подходит.
4. Проверить сценарии на разных формулировках, исправлениях, смене темы,
   повторной доставке, ошибках и исчерпании лимитов. Измерять время, токены,
   число вызовов и долю завершённых задач отдельно по ролям.

Отдельная графовая база данных для этих исправлений не требуется. Её необходимость
следует оценивать по конкретным задачам поиска связанной информации.
