**Вывод:** AirHop уже имеет существенное операционное ядро для работы центра. Следующий разумный рубеж — управляемый пилот с узко объявленными возможностями, после устранения перечисленных ниже блокеров. Готовность к самостоятельному подключению произвольного центра и обещанию полного обслуживания родителей пока не доказана. Особенно велик разрыв между целевым Hermes из спецификации и его нынешними инструментами.

Процент готовности здесь был бы обманчив: расписание может быть хорошо реализовано, но одна ошибка доставки или неработающий первый вход блокирует весь пользовательский путь.

**Подтверждённые проблемы и существенные разрывы**

**1. WhatsApp: «API принял» превращается в «доставлено». Приоритет P1, блокер запуска WhatsApp с обещанием надёжных уведомлений.**

После успешного `send_text` gateway сразу вызывает `complete_delivered`. Обработчик webhook читает `value.messages`, но не обрабатывает `value.statuses`. Значит, последующий статус `failed` не исправляет уже сохранённый результат, а сотрудник может считать родителя уведомлённым.

Локальное воспроизведение на существующих FakeGraph/FakeClient и временной SQLite:

```text
After Graph API acceptance: ['delivered']
Signed failed-status webhook HTTP: 200
After failed webhook: ['delivered']
```

В сеть сообщения не отправлялись. Точки: [обработка webhook](/Users/andreymakeev/Developer/airhop-center/integrations/hermes-airhop-channel-gateway/src/airhop_hermes_gateway/whatsapp.py:393), [завершение outbound](/Users/andreymakeev/Developer/airhop-center/integrations/hermes-airhop-channel-gateway/src/airhop_hermes_gateway/whatsapp.py:606). Meta отдельно определяет статусы `sent`, `delivered`, `read`, `failed`: [официальная коллекция Meta](https://www.postman.com/meta/whatsapp-business-platform/folder/fuaee8l/statuses-object).

Сделать: разделить принятие провайдером и доставку пользователю; сохранять status webhooks с dedupe, привязкой к provider message ID и защитой от неверного порядка; отражать финальную ошибку и необходимое действие сотрудника. Критерий: успешный POST, затем `failed` → видимая недоставка; повтор и поздний статус не портят более новое состояние и не повторяют Booking.

**2. WhatsApp-чат ещё не замыкает путь «сайт → заявка → подтверждённый родитель». Приоритет P1 для бразильского запуска.**

В `booking_handoff.rs` выбор канала и redeem ограничены `telegram`; HTTP-схема принимает `confirmationChannels` только из `z.literal("telegram")`. Собственная WhatsApp app и прямой чат не дают эквивалентного безопасного подключения уже созданной заявки.

Основания: [handoff](/Users/andreymakeev/Developer/airhop-center/crates/buzz-db/src/airhop/booking_handoff.rs:52), [публичный API](/Users/andreymakeev/Developer/airhop-center/crates/buzz-relay/src/api/airhop_public.rs:1117), [клиентская схема](/Users/andreymakeev/Developer/airhop-center/desktop/src/features/booking/data/httpPublicBookingService.ts:83).

Сделать: общий provider-aware grant/binding, безопасное продолжение заявки в WhatsApp и отображение фактической связи в UI. Проверить replay, expiry, чужую семью, повторное открытие ссылки и повтор сообщения. Для пилота через Telegram это не обязательный блокер; для WhatsApp-first продукта — обязательный.

**3. Отложенные WhatsApp-сообщения упираются в templates. Приоритет P1 для уведомлений.**

Снаружи сохранённого 24-часового окна код завершает доставку с `whatsapp_template_required`; синхронизация/отправка templates отсутствует. Подтверждение, которое сотрудник подготовил позже, и будущее напоминание нельзя считать покрытыми текстовым adapter. Граница явно отражена в [gateway README](/Users/andreymakeev/Developer/airhop-center/integrations/hermes-airhop-channel-gateway/README.md:127). Наличие ограниченного окна также описано в [документации Meta SDK](https://whatsapp.github.io/WhatsApp-Nodejs-SDK/).

Сделать: минимальный набор одобренных service templates, актуальные данные при отправке, проверку получателя/подписки, обработку недоступного template и понятный human fallback. Не расширять этот пакет до маркетинговой рассылки.

**4. Handoff Hermes может упереться в собственный лимит чтений. Приоритет P1 для устойчивости, ранее диагностирован как P2 дефект графа.**

После контекста и пяти чтений назначение филиала очищает context. Новый context уже запрещён лимитом шести чтений; `send_parent_reply` с handoff при отсутствии кэша запрашивает этот же context ради адресатов. Путь передачи человеку может заблокироваться именно тогда, когда он нужен. Также обычная отправка не требует предварительной загрузки context: `validate_reply` проверяет форму ответа, но не это условие.

Предыдущий аудит содержит локальное воспроизведение; в текущих исходниках условия сохранились: [лимиты/сброс](/Users/andreymakeev/Developer/airhop-center/crates/buzz-dev-mcp/src/airhop/parent_dialogue.rs:112), [путь отправки](/Users/andreymakeev/Developer/airhop-center/crates/buzz-dev-mcp/src/airhop.rs:1420). Это не доказанный обход серверных прав. Сделать отдельный ограниченный гарантированный путь получения актуальных handoff targets, общий допуск отправки и постоянные regression tests. Не снимать все лимиты.

**5. Семейная идентификация и дубли не доведены до рабочего цикла. Приоритет P1 перед подключением существующих центров.**

Первая безопасная привязка Telegram есть. Целевые `FamilyInviteGrant` и `FamilyAccessRequest` второго родителя не найдены в моделях/API/миграциях. Совпадение введённого телефона правильно не даёт доступ к семье. Но в UI сейчас видны предупреждения о дублях, а полноценная операция их проверки/разрешения не обнаружена.

Сделать: сотруднику — очередь кандидатов, подтверждение «тот же человек / другой», корректная привязка с audit; родителю — один проверяемый сценарий подключения второго взрослого. Отдельно проверить повторное обращение существующего клиента. Не заменять этот процесс автоматическим объединением по телефону или фамилии. Основания: [требования](/Users/andreymakeev/Developer/airhop-center/docs/AIRHOP_SOURCE_OF_TRUTH.md:840), [создание duplicate candidates](/Users/andreymakeev/Developer/airhop-center/crates/buzz-db/src/airhop/family_lifecycle.rs:561), [предупреждение карточки](/Users/andreymakeev/Developer/airhop-center/desktop/src/features/booking/ui/ServerFamilyDetailsScreen.tsx:242).

**6. Важные обещания спецификации ещё не имеют инструментов.**

Не обнаружены связанные исполняемые контуры для `PaymentClaim`, структурированных `ParentPaymentInstruction`, родительских payment reminders, `LessonParticipationNotice`, `TeacherMessageRequest`/`TeacherParentMessage`, `RelationshipMemoryFact`, полного typed `HermesQualityIncident`. Текущее меню родительских операций компактно и явно перечислено в [AgentBackendRequest](/Users/andreymakeev/Developer/airhop-center/crates/buzz-relay/src/api/airhop_agent_backend.rs:303).

Их нужно разделить по очереди внедрения:

- До обещания полного обслуживания: безопасное «я оплатил» с задачей человеку; отсутствие/опоздание; напоминание о занятии; реальные файлы для сотрудника; понятное разрешение переноса.
- После устойчивого пилота: family memory, teacher feedback и ограниченный versioned learning. Наличие консультационной аналитики не равно автоматическому обучению агента.
- Глубокие графы развития ребёнка, автоматические наблюдения и межпродуктовые экспорты можно отложить.

История хода, bounded context, receipts и runtime recovery уже существуют. Не следует описывать нынешнего Hermes как полностью лишённого состояния. Generic profile memory осознанно [отключена](/Users/andreymakeev/Developer/airhop-center/integrations/hermes-airhop-parent-runtime/config.yaml:5).

**7. Медиа пока не достигают сотрудника как исходные вложения. Приоритет P1 для обычного родительского общения.**

Gateway сохраняет notice о неподдерживаемом содержимом, но не скачивает оригинал и не расшифровывает голос. Это безопасная деградация, но не реализация целевого media flow из §6.6. Чек, голосовое или фото не должны превращаться в обещание «передал сотруднику», если оригинал недоступен. Основание: [текущая граница](/Users/andreymakeev/Developer/airhop-center/integrations/hermes-airhop-channel-gateway/README.md:134).

Сделать сначала защищённый оригинал в staff thread и понятное состояние обработки; затем voice transcription с provenance, лимитами и fallback. Vision и генерация голоса не нужны для первого запуска.

**8. Требования к правам сотрудников расходятся с текущей моделью. Приоритет P1 перед расширением команды центра.**

Начальный MVP опирается на Buzz membership без отдельных AirHop ролей. В целевой спецификации уже указаны ограничения обычного сотрудника по филиалу/роли и минимальные данные преподавателю. В общей staff API-проверке человеческий member получает tenant scope; дополнительные owner/admin ограничения применяются к integration access, а не универсально к каждому staff read/write. Branch responsibility определяет уведомления, не ACL.

Это не cross-tenant утечка и не основание объявлять все данные публичными. Но нельзя обещать «преподаватель видит только свой филиал», пока endpoint-уровень этого не обеспечивает. Основания: [staff auth](/Users/andreymakeev/Developer/airhop-center/crates/buzz-relay/src/api/airhop_staff.rs:2978), [целевая видимость](/Users/andreymakeev/Developer/airhop-center/docs/AIRHOP_SOURCE_OF_TRUTH.md:809), [граница shared channels](/Users/andreymakeev/Developer/airhop-center/integrations/hermes-airhop-channel-gateway/README.md:99).

Сделать матрицу owner/admin/administrator/teacher/agent и серверные проверки на нужных ресурсах. В раннем пилоте можно ограничить доступ доверенными руководителями, явно закрепив это ограничение.

**9. Публичная публикация macOS опережает финальную проверку. Приоритет P1 для процесса выпуска.**

В [AirHop release workflow](/Users/andreymakeev/Developer/airhop-center/.github/workflows/airhop-macos-release.yml:82) `tauri-action` выполняет создание GitHub release с `releaseDraft: false`, а следующий шаг запускает `codesign`, `spctl` и `stapler validate`. Если эта проверка упадёт, публикация уже могла произойти. Этот workflow также не содержит явного ожидания успешного продуктового CI для выбранной ревизии.

Сделать: сначала собрать непубличного кандидата, проверить подпись, notarization и необходимые тесты, затем публиковать и обновлять download manifest. Критерий: намеренно невалидный кандидат не становится доступным пользователям. Это вывод о порядке шагов в коде, а не сообщение о реально опубликованном плохом релизе.

**Что стоит добавить для жизнеспособного продукта**

1. **Ввод существующей базы.** Импорт CSV с сопоставлением колонок, preview, валидацией дат/телефонов, dry-run и отчётом ошибок; экспорт клиентом собственных операционных данных. Даже если pilot setup сначала выполняет команда, нужен повторяемый путь без ручного SQL.
2. **Один экран «Центр готов к работе».** Организация, расписание, тарифы, знания, сотрудники, канал, тестовая заявка, домен и доставка — с конкретным незавершённым шагом. Использовать существующие серверные статусы, не рисовать общий зелёный индикатор по запущенному процессу.
3. **Управление исключениями.** В одном понятном списке: дубль, запрос переноса, неподтверждённый родственник, неразобранная оплата, недоставка и обращение без ответственного. Исполнение и закрытие каждой задачи должны оставлять историю.
4. **Проверяемое качество агента.** Versioned golden dialogues на языках запуска, флаги опасного ответа и остановка отдельного cycle; тесты результата и действия, а не точной фразы. Текущий offline staff-intent eval не заменяет parent semantic eval реального model runtime.
5. **Экономика эксплуатации.** Измерять стоимость успешной записи/решённого обращения, input/output tokens, provider/template расходы, число повторов и минуты ручной поддержки. Не вводить тарификацию по ощущениям от одного диалога.
6. **Поддержка и восстановление владельца.** Короткая пользовательская инструкция, проверенный перевыпуск кода/ключа, контроль доступа при увольнении, сбор минимальной диагностики по версии и incident ID.
7. **Явный рынок первого выпуска.** Сейчас owner selector разрешает только English/Русский. Португальские словари есть, но этого недостаточно для обещания полностью бразильского рабочего интерфейса. Для Brazil-first нужны принятые pt-BR путь владельца, публичная форма, Hermes и реальные WhatsApp сценарии. Для RU-first разумнее сначала завершить Telegram; MAX объявлять будущей интеграцией.

**Что можно отложить**

Новый агентный framework, универсальный knowledge graph, графовая БД, автоматическое самообучение, диаграммы развития ребёнка, маркетинговые кампании, MAX и дополнительные каналы, собственное родительское мобильное приложение. Для центров с пакетами, заморозками и отработками абонементный учёт уже станет отдельным обязательным пакетом.

Мобильный путь по источнику истины — подключение сотрудника через Buzz; родителю достаточно сайта и мессенджера. Не следует расширять первый запуск до ещё одного приложения.

**Документация требует консолидации**

В источнике истины дата «последнее обновление» — 5 сентября, хотя внутри есть уточнения после неё. В §5 ещё условно описывается будущая база знаний, а §3 уже содержит implementation contract и код существует. Старый readiness backlog включает knowledge, branch responsibility и WhatsApp как будущие работы, хотя они реализованы полностью или частично. Release guide называет текущим кандидатом 0.5.6 и миграцию 58; desktop сейчас 0.5.12, последний описанный demo rollout — миграция 64, рабочая миграция — 65. Кроме того, старое утверждение «секреты каналов не входят в Center» конфликтует с новым encrypted credential store в Relay.

Сделать одну компактную release matrix: требование → implementation → тест → deployed version → live acceptance → остаток. Исторические rollout notes сохранить с явной пометкой даты/замены. Без этого следующие задачи будут повторно реализовывать уже сделанное или принимать желаемое за готовое.
